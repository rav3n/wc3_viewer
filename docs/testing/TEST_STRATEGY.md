# Стратегия тестирования

Статус: v0.1 · 2026-10-27. Основа: [PRD](../product/PRD.md), [ARCHITECTURE](../architecture/ARCHITECTURE.md), [W3G_FORMAT](../architecture/W3G_FORMAT.md).

Решения пользователя, которые проверяют тесты:

- только 1v1, только патч 3.0+ (`version ≥ 10200`);
- UI на английском;
- таргет UI — Kotlin/JS (не Wasm);
- EPM = APM без повторов (правило — в §5);
- победитель: есть leave с `result = 0x09` → winner, иначе `Unknown`;
- слот FLO (pid 24, team 24) — наблюдатель W3C, в игроки не попадает;
- `raceFlag 0x20` = Random.

Фикстуры и эталоны — в [`testdata/`](../../testdata/README.md).

## 1. Пирамида по модулям

| Модуль | Что тестируем | Где | Вид |
|---|---|---|---|
| `:core:binary` | `ByteReader`: LE u8/u16/u32/f32, cstr, fourcc, выход за границы → исключение, не мусор. `Inflater`: побайтовое совпадение с `java.util.zip.Inflater` на всех блоках всех фикстур; незавершённый поток (sync flush без final-блока) отдаёт данные без ошибки | `commonTest` → jvm + js | unit, сверка, property |
| `:data:parser` | Header/SubHeader, блоки, метаданные, слоты, Reforged-чанки, TimeSlot, все action-ы из W3G_FORMAT §7.1, сдвиг ID ≥ 0x77 (§7.3), golden на всех фикстурах, негативные кейсы, fuzz | `commonTest` (синтетика) → jvm + js; golden и fuzz — `jvmTest` | unit, golden, негативные, fuzz |
| `:analytics` | APM (правило w3gjs), EPM, хоткеи, билд-ордер, тайминги, герои, оценки экономики и армии. Вход — синтетические списки `GameEvent`, без парсера. Плюс golden по эталонам | `commonTest` → jvm + js | unit, golden |
| `:presentation` | `ReplayViewModel`: переходы `Empty → Loading → Loaded/Failed`; маппинг `AnalysisReport → SectionUi`; тексты ошибок; пометка «estimate» у оценочных рядов. Парсер и метрики — фейки | `commonTest` → jvm (+ js) | unit |
| `:app:web` | Чтение файла, drag-and-drop, рендер экранов, отзывчивость при разборе | браузер | smoke (`jsBrowserTest`), ручной чек-лист (§10) |

Соотношение: основная масса — unit в `commonTest`; golden — по одному тесту на фикстуру; браузер — smoke и замер скорости.

### JVM и браузер

- Вся логика (`commonMain`) гоняется на jvm — быстрый цикл и доступ к файлам `testdata/`.
- Те же `commonTest` гоняются в браузере (`jsBrowserTest`, headless Chrome). Цель — поймать платформенные различия Kotlin/JS:
  - `Int`/`Long` и знаковость: u32 > 2³¹ (`0xFFFFFFFF` в NetTag), сдвиги `ushr`/`shr`;
  - `Float` (Vec2 в 0x11/0x12): JS считает в double;
  - строки UTF-8 с CJK и корейскими BattleTag (`多情剑客无情剑#4716`, `굴렁굴렁굴렁쇠#31873`);
  - округление APM: `.5` округляется вверх (как `Math.round` в w3gjs и `roundToInt` в Kotlin). Генератор эталонов делает так же (`floor(x + 0.5)`, не Python `round`).
- Хотя бы один golden в браузере: самая маленькая фикстура `6ae0b88c01d5ffcb2ad75cb0.w3g` (157 КБ). Способ доставки в тест (ресурс Karma, base64-константа из Gradle-task) выбирает программист.
- Wasm не таргет. Если `wasmJs` останется в сборке (как в ARCHITECTURE §2), гонять там те же `commonTest`, но не блокировать ими CI.

## 2. Golden-тесты на реальных реплеях

Фикстуры: `testdata/replays/3.00/*.w3g` (21 файл 1v1). Командные реплеи (`testdata/replays/team/`) — только для негативного теста «Only 1v1», эталонов у них нет. Эталоны: `testdata/expected/<файл>.json`. Генератор — независимый Python-скрипт, не Kotlin (см. `testdata/README.md`).

Что сравниваем и с какой точностью:

Кроме полей эталона, golden-тест проверяет инварианты:

- `parse.unknownActions` пуст, `ParseDiagnostic` нет;
- события `Replay.events` отсортированы по времени;
- `|durationMs − gameTimeSumMs| ≤ 50 мс` **только для реплеев без паузы** (в `Replay_2026_09_16_0103` пауза 39 с — разница 38 986 мс, см. §12);
- у каждого игрока `skillsLearned ≤` числа очков навыков на конец игры (сверено с W3C API, см. `w3cApiCheck` в эталоне).

Обновление эталона = осознанное изменение. Каждое изменение `testdata/expected/*.json` — отдельным коммитом с причиной.

## 3. Внешний эталон: W3Champions API

`testdata/w3c-api/<w3cMatchId>.json` — ответы `GET https://website-backend.w3champions.com/api/matches/{id}` для всех 21 реплея 1v1. Сопоставление реплея и матча: `gameName` реплея = `w3c-<gateway>-<original-ongoing-match-id>[-…]`. ID может содержать `-` (`j-CTAyD4XV`), поэтому сравнивать префикс, а не `split('-')`.

## 4. APM по правилам w3gjs

Источник: w3gjs 4.3.0, `W3GReplay.handleActionBlock` и `Player.ts`. Эталонное поле — `apmW3gjs`.

1. Учитываются action-ы: `0x10, 0x11, 0x12, 0x13, 0x14, 0x17, 0x18, 0x1C, 0x1D, 0x1E, 0x61, 0x66, 0x67`. `0x65` в switch есть, но счётчик не растёт — не считается.
2. `0x16` (смена выделения): `mode = 0x02` (deselect) — +1 и флаг «был deselect». `mode = 0x01` (select) — +1, только если флага нет; затем флаг сбрасывается. Флаг сбрасывается и в начале каждого CommandBlock. Итог: пара deselect+select = 1.
3. Не считаются: `0x19, 0x1A, 0x1B, 0x77, 0x7A` и всё остальное.
4. Знаменатель — время последнего CommandBlock игрока (`lastCommandBlockMs`), а не длительность реплея.
5. `apm = Math.round(count / (lastCommandBlockMs / 60000))`, `0` если игрок не действовал.

ID — в нумерации файла 3.0 (W3G_FORMAT §7.3). Учитываемые ID < 0x77, сдвиг на них не влияет.

## 5. EPM

Правило пользователя: EPM = APM без повторов. Повтор (не считается):

- тот же приказ (тот же action ID, тот же order, та же цель — точка или объект) от того же игрока в пределах 500 мс от предыдущего такого же;
- повторное выделение той же группы юнитов (тот же набор NetTag) подряд;
- повторный выбор той же хоткей-группы подряд.

Unit-тесты на синтетических событиях (`:analytics`):

| Кейс | Ожидание |
|---|---|
| Два одинаковых right-click в одну точку, интервал 499 мс | 1 в EPM |
| То же, интервал 500 мс | 2 (граница включительная/исключительная — зафиксировать в коде и тесте; предлагаем «< 500 мс = повтор») |
| Два right-click в разные точки, 100 мс | 2 |
| 10 кликов в одну точку с шагом 100 мс | 1: окно отсчитывается от предыдущего повтора, а не от первого — **согласовать**, иначе получится 2 |
| `0x18 group 1`, `0x18 group 1` | 1 |
| `0x18 group 1`, `0x18 group 2`, `0x18 group 1` | 3 |
| Выделение {A,B}, выделение {A,B} | 1 |
| Выделение {A,B}, выделение {B,A} | 1 (набор, не порядок) |
| Повтор у разных игроков | не схлопывается |
| EPM ≤ APM | на всех фикстурах, property |
| Доля спама `(APM − EPM)/APM` ∈ [0; 1] | на всех фикстурах |

Golden для EPM не заводим, пока правило не зафиксировано в коде. После — дописать `epm` в генератор эталонов тем же правилом.

## 6. Герои и навыки

Найдено на сверке с API: игрок часто шлёт приказ на изучение навыка дважды за ~120–150 мс (двойной клик). Второй приказ не проходит, но в реплее он есть. Пример: `k0st34ka#2723`, `AHtc` в 544 200 и 544 350 мс; Mountain King в API — уровень 4, сырых приказов — 5.

Правило в эталоне: повтор **того же** навыка тем же игроком < 500 мс от предыдущего такого же — одно изучение. С ним 20/21 файл проходят «изучено ≤ уровня из API». Нижняя граница уровня в PRD («каждое умение = +1 уровень») без этого правила завышена.

Правило не точное, контрпример — `6ae0bcf8` (`KuaMax#1136`):

- Archmage: после `tret` (Tome of Retraining, 1 863 900 мс) игрок за 450 мс трижды учит `AHbz` и дважды `AHab`. Это законная раздача очков заново. Дедупликация схлопывает её до 2, а без учёта `tret` старые навыки тоже остаются в счёте: итог 7 при уровне 5 в API.
- Paladin: 4 изучения с интервалами > 500 мс при уровне 3 в API. Один приказ не прошёл (не было очка), и по реплею это не видно.

Выводы для `:analytics`:

- после `tret`/`tert` счёт навыков героя сбрасывать (как `inferHeroAbilityLevels` в w3gjs);
- «нижняя граница уровня» — оценка, а не гарантия. Помечать в UI как estimate;
- golden-тест «изучено ≤ уровня» для `6ae0bcf8` пока исключить с этой ссылкой.

Порядок героев в эталоне — по первому изучению навыка. Приказ найма ≠ появление: `Tak#31483` заказал Archmage на 94 с, но первый навык Archmage изучил на 610 с, а Dark Ranger — на 141 с. Тесты таймингов героев проверяют этот кейс.

## 7. Негативные кейсы

Ожидаемое поведение — из ARCHITECTURE §5.2: фатальны только битый header и битый zlib; остальное — `ParseDiagnostic`. Сообщение пользователю — на английском.

| Вход | Фикстура | Ожидание |
|---|---|---|
| Файл 0 байт | `testdata/replays/broken/` × 4 | `ReplayFormatException(EMPTY)`, UI: «File is empty» |
| 343 009 нулевых байт | `broken/Replay_2026_09_14_2320.w3g` | `ReplayFormatException(NOT_A_REPLAY)` — нет magic. Не зависать на `indexOf` по большому буферу |
| Не реплей (PNG, текст, `.w3g` с мусором) | генерировать в тесте | `NOT_A_REPLAY` |
| Мусор перед magic | префикс 512 байт к рабочей фикстуре | Разбирается как обычно (w3gjs ищет magic через `indexOf`) |
| Обрезан посередине сжатого блока | рабочая фикстура, срез на N байт | Разбираются целые блоки; диагностика «truncated»; `Replay` с частью событий **или** понятная ошибка — **решить** и зафиксировать тестом |
| Обрезан ровно по границе блока | то же | То же, без падения |
| `blockCount` больше фактического | патч header | Диагностика, не исключение вне `ReplayFormatException` |
| `compSize` блока > остатка файла | патч заголовка блока | `ReplayFormatException(CORRUPTED)` или усечение |
| `decompressedSize` = 0xFFFFFFFF, `blockCount` = 0xFFFFFFFF | патч header | Отказ до выделения памяти (лимит 64 МБ) |
| Битый zlib в блоке K | flip байта в данных блока | `CORRUPTED` либо события до блока K + диагностика |
| Не 1v1: 2 игрока + наблюдатель-человек | синтетика слотов | Наблюдатель отфильтрован, разбор идёт |
| Не 1v1: 3+ игроков не-наблюдателей | синтетика слотов (реальных 2v2 нет) | `UNSUPPORTED_MODE`, UI: «Only 1v1 replays are supported» |
| Старая версия: `version < 10200` | патч SubHeader | `UNSUPPORTED_VERSION` с номером патча в сообщении |
| `headerVersion = 0` | патч header | `UNSUPPORTED_VERSION` |
| Product `WAR3` (RoC) | патч | `UNSUPPORTED_VERSION` |
| Неизвестный action ID (`0xF0`) в CommandBlock | патч распакованного потока | Остаток CommandBlock пропущен, `ParseDiagnostic` с временем и смещением, следующий блок разобран, итоговые счётчики остальных блоков совпадают с эталоном |
| Известный action с длиной больше остатка CommandBlock | патч | Как неизвестный: пропуск остатка, диагностика |
| `0x16` с `n = 65535` | патч | Выход за CommandBlock → диагностика, без аллокации 512 КБ на каждый такой action |
| TimeSlot с `byteCount < 2` | патч | Нет бесконечного цикла и отрицательной длины |
| cstr без завершающего `0x00` (имя игрока, карта, 0x77) | патч | Ошибка с границей, не чтение до конца буфера |
| Неизвестный блок верхнего уровня (не из таблицы §6) | патч | Остановка разбора игровых блоков + диагностика; метаданные и уже разобранные события сохраняются |
| playerId в CommandBlock не из слотов | патч | Блок пропущен + диагностика (так делает w3gjs) |
| Нет leave-блоков вообще | срез после последнего TimeSlot | `winner = Unknown`, длительность — из SubHeader |
| Все leave `0x07` | `Replay_2026_10_23_0033`, `_0240` | `winner = Unknown` |
| Leave `0x09` у FLO (pid 24) | `Replay_2026_09_16_0103` | **Не** победитель: правило применять только к игрокам |
| Leave `0x09` у обоих игроков | синтетика | `Unknown` + диагностика |

Ошибки контейнера — sealed-тип с причиной (`EMPTY`, `NOT_A_REPLAY`, `UNSUPPORTED_VERSION`, `UNSUPPORTED_MODE`, `CORRUPTED`). Имена — предложение, финальные — за программистом. Тест `:presentation` проверяет текст для каждой причины.

## 8. Property и fuzz

Цель: никакой вход не роняет парсер вне `ReplayFormatException` и не вешает его.

Генераторы входа (seed фиксирован и печатается при падении):

1. Случайная порча N ∈ {1, 8, 64} байт рабочей фикстуры — в header, в сжатых данных, в любом месте.
2. Порча **распакованного** потока. Нужна тестовая точка входа после inflate (например, `internal fun parseDecompressed(header, bytes)`). Без неё почти вся порча ловится zlib и до разбора action-ов не доходит.
3. Обрезка по каждой позиции с шагом 1 в первых 4 КБ и с шагом 997 дальше.
4. Полностью случайные массивы длиной 0..64 КБ, с magic в начале и без.
5. Мутации полей длины: `byteCount`, `actionBlockLength`, `n` в 0x16/0x17, длины cstr, `bytesRemaining` в 0x19, `length` Reforged-чанка → 0, 1, max-1, max.

Инварианты:

- результат — `Replay` или `ReplayFormatException`; другие исключения (`IndexOutOfBounds`, `IllegalArgument`, `OutOfMemoryError`) — дефект;
- время разбора одного входа ≤ 2 с на jvm (таймаут теста). Зависание — дефект;
- каждый цикл чтения продвигает смещение (ловится таймаутом);
- распакованный размер ≤ 64 МБ;
- для `Replay`: события отсортированы, `time ≥ 0`, у каждого события `player` из списка игроков;
- `:analytics` на любом `Replay` из fuzz не бросает исключений, APM ≥ 0, EPM ≤ APM.

`Inflater`: property-тест «случайные данные → сжать `java.util.zip.Deflater` с `SYNC_FLUSH` → распаковать нашим = исходник», плюс случайный мусор на вход → нет крэша.

Объём: в CI на jvm — 1 000 итераций на генератор; локально и раз в сутки — 100 000. Найденный падающий вход сохранять в `testdata/fuzz-regressions/` как регрессионную фикстуру.

## 9. Производительность

Бюджет PRD §5: разбор и расчёт типичного 1v1 — до 1 с на среднем ноутбуке; UI не блокируется. ARCHITECTURE §8: Worker нужен, если на реальном устройстве > 100 мс.

| Тест | Где | Порог |
|---|---|---|
| `parse + analyze` самой тяжёлой фикстуры `6ae0bcf801d5ffcb2ad75e54.w3g` (646 КБ, 35 мин, 17 675 CommandBlock) | `jsBrowserTest`, headless Chrome, `performance.now()`, медиана из 5 после прогрева | ≤ 1000 мс — fail; > 100 мс — предупреждение (сигнал к Worker) |
| То же, все 10 фикстур | jvm, после прогрева JIT | для трендов, не гейт |
| Длинный синхронный участок | браузер: `PerformanceObserver('longtask')` во время разбора | ни одной задачи > 50 мс, иначе `yield()` реже, чем каждые 2000 TimeSlot |

### Каких реплеев не хватает (попросить у пользователя)

Приоритет 1 — закрывает риски парсера и решения пользователя:

1. Игра с очень высоким APM (300+) и длительностью 40+ мин — сейчас длинная игра идёт на APM 47–74, а нагрузку даёт число действий.
2. Ничья или дисконнект обоих; матч, где проигравший вышел без экрана поражения.
3. Реплей того же матча, записанный каждым из игроков, — проверить, зависит ли leave-результат от того, кто записал (в `Replay_*` RavenGG проиграл 2 из 3, и именно в них у всех `0x07`).
4. FFA или custom с 3+ игроками в разных командах (2v2 и 4v4 уже есть).
5. Реплей 2.0.x и 1.36 (или любой < 3.0) — для отказа «unsupported version» и границы сдвига ID 0x77 (W3G_FORMAT §10.1).
6. Реплей не с W3C: Battle.net ладдер или LAN, без FLO.

Приоритет 2 — покрытие метрик:

7. Игра с паузой и возобновлением от разных игроков, с несколькими паузами.
8. Воскрешение героя в алтаре и таверне, найм наёмников. Ещё один реплей с Tome of Retraining — проверить сброс навыков.
9. Игра с передачей ресурсов (0x51) — в 1v1 вряд ли, достаточно custom (или командные из `team/`, если там есть).
10. Наблюдатель-человек в лобби (не FLO).
11. 1v1 на Scrimmage и остальных картах пула 3.0.

## 12. Проблемы в формате и документах

Найдено при генерации эталонов и сверке. Решения — за автором документа или программистом.

1. **ARCHITECTURE §2, §9 ADR 3**: UI-таргет — `wasmJs` основной + `js` fallback. Пользователь решил: Kotlin/JS, не Wasm. Документ не обновлён.
2. **ARCHITECTURE §4.4 EPM**: «повтор в пределах 200 мс; выделение без последующей команды не считается». Решение пользователя: 500 мс, повтор выделения и хоткей-группы. Документ не обновлён.
3. **ARCHITECTURE §10.1**: «leave-блоки дают одинаковый 0x07 для обоих» — устарело. W3G_FORMAT §6.2 и сверка: в файлах `6ae0…` есть `0x09` у победителя (18/18).
4. **W3G_FORMAT §7.1**: «по правилам w3gjs примерно 166 / 198 APM» для `_0240`. Это все `0x16` без учёта пары deselect+select. По правилам w3gjs — **146 / 182**.
5. **W3G_FORMAT §3, ARCHITECTURE §5.3**: «сумма timeIncrement расходится с длительностью на ≤ 6 мс / ±50 мс». Неверно для реплея с паузой: `Replay_2026_09_16_0103` — пауза 39 001 мс (0x01 на 773 010, 0x02 на 812 011), header 1 153 725, сумма 1 192 711. Header не учитывает паузу. Инвариант — только для реплеев без паузы, или `header ≈ сумма − длительность пауз`.
6. **Длительность матча**: в файлах `6ae0…` SubHeader-длительность на 45–50 с больше последнего leave игрока — FLO остаётся в игре. В UI показывать `matchEndMs` (последний leave игрока), иначе график и «длительность» врут на ~50 с. В PRD/ARCHITECTURE не описано.
7. **W3G_FORMAT §6.2**: в `Replay_2026_09_16_0103` leave **FLO** (pid 24) имеет `result 0x09`. Правило «0x09 → winner» нужно применять только к игрокам после фильтра наблюдателей.
8. **PRD §3 «Нижняя граница уровня героя»**: без дедупликации двойных кликов граница завышена (3 героя > уровня из API в первых 10 файлах). После Tome of Retraining и при неудачных приказах (`6ae0bcf8`) завышена даже с дедупликацией. Это оценка, не граница (§6).
9. **PRD §3 «Время героя»**: приказ найма не равен появлению (`Tak#31483`, Archmage). Для таймингов героев первый навык надёжнее приказа.
10. **W3C API**: `durationInSeconds` — реальное время, не игровое; порядок героев не хронологический. Как эталон длительности и порядка не годится.
11. **gameName**: `original-ongoing-match-id` может содержать `-`. Если парсер когда-нибудь извлекает ID матча W3C из `gameName`, не делить по `-`.
12. **ARCHITECTURE §3**: фикстуры в `testdata/replays/` (+ «ожидаемые JSON-снимки» там же). Фактическая раскладка: `testdata/replays/3.00/`, `testdata/replays/broken/`, эталоны отдельно в `testdata/expected/`.
13. **Эвристика w3gjs для победителя** (reason `0x0C` → winner) на `Replay_2026_10_23_0033`/`_0240` дала бы правильный ответ, но случайно: все leave в одном тике, выбирается первый по порядку блок. Решение «Unknown» корректно.
